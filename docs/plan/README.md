## 编写与更新

计划开头说明状态、当前事实源和目标。正文按以下职责组织：

| 内容 | 要求 |
|---|---|
| 背景与现状 | 记录规划基线，指出需要解决的耦合或缺口，给出源码或资源依据 |
| 目标与边界 | 说明预期行为、允许改动范围及与其他任务的关系 |
| 技术依据 | 区分源码事实、实机观察与假设，保留影响选择的证据 |
| 方案与步骤 | 标明职责、数据流、改动落点、执行顺序和每步完成条件 |
| 技术选择 | 记录方案结论及必要理由 |
| 风险与限制 | 区分已知限制与假设，并写明处置 |
| 验证与待确认项 | 列出自动检查和用户验收条件，标出执行前提 |

计划允许记录临时目标与验收状态。保持状态准确，技术选择记录方案依据；讨论流水、AI 修改记录和修订自述从正文删除。行号可用于规划基线定位，当前事实优先引用类型、方法和资源 ID。

## 完成与归档

1. 满足计划的完成条件；需要用户实机验收的，保留到验收完成。
2. 将已落地行为同步到对应权威文档，核对当前入口与链接。
3. 移入本地 `docs/archive/`，保留文件名；同名冲突使用完成日期后缀。
4. 更新本地 `docs/archive/README.md`，从本页删除完成条目；公开文档的链接指向现行资料。

归档目录和 `.scratch/` 沿用 Git 忽略策略。本地历史材料由归档索引管理。
