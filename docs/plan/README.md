# 实施计划文档规范

`docs/plan/` 存放**进行中**的子系统改造规划，实施完成后移入 `docs/archive/`（该目录已列入 `.gitignore`，只本地留存）。

计划文档**不构成机制权威**：它记录的是改造背景、核实依据与决策记录。任何机制的唯一权威描述永远是 [`docs/dev/`](../dev/README.md) 下对应的子系统文档。计划文档里的机制描述在实施完成后应同步到权威文档，本目录只保留背景与决策。

## 统一结构

结构参考已归档的 `advancement-tree-plan.md`、`panning-variants.md`、`shimmer-worldgen-feature.md`，统一为九章：

| 章 | 章节 | 必填 | 内容要求 |
|---|---|---|---|
| — | 状态块 | 是 | 文档顶部引用块：状态与日期、与 `docs/dev/` 权威文档的关系（计划文档不构成机制权威）、修订记录 |
| 一 | 现状 | 是 | **实施前**的真实状态：现有实现（组件 / 文件 / 职责）、需要改造的耦合点（精确到 `文件:行`）、现存缺陷；显式声明「本节记录的是实施前状态」 |
| 二 | 目的 | 是 | 目标能力或新增内容、架构目标、**明确不做（本轮范围外）** |
| 三 | 技术原理 | 是 | 路线选择的依据：已核实的机制事实，逐条标注证据等级（源码核实 / 字节码核实 / 数据包核实 / 实机确认 / 推算），以「为什么选 X 而不是 Y」组织；末尾给「必须遵守的边界」 |
| 四 | 技术路线 | 是 | 分层设计与目标结构、关键类型（API 草案）、数据流、文件改动清单、分阶段实施、文档同步 |
| 五 | 决策记录 | 是 | 编号表（决策点 / 结论），记明被否决的备选与理由，以及**讨论中修正的自身错误留档** |
| 六 | 风险与限制 | 是 | 表格：风险 / 说明 / 处置 |
| 七 | 验证方式 | 是 | 区分「编译验证（开发执行）」与「实机验证（用户执行）」，并列出重点核对项 |
| 八 | 待确认项 | 否 | 尚未裁决或刻意推迟的事项与推荐处置 |
| 九 | 实施结果 | 完成后追加 | 带日期的实施结果：构建结果、产物检查、与计划的偏离、待用户实机验证项 |

## 格式约定

- 章节用中文序号（一、二、三…），子节用 `x.y`。
- 事实要么给出证据标注，要么明确标为推断；不写无来源的确定性断言。
- 文件引用精确到 `文件:行`，并注意行号会随实施失效。
- **机制描述不写进计划文档**：实施完成后把机制同步到 `docs/dev/` 对应权威文档，计划文档只保留背景、核实依据与决策记录。
