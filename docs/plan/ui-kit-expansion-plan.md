### 1.3 能力缺口

现有 kit 没有通用的纵向滚动容器、控件集合命中、横纵组合布局、键盘焦点与语义样式。这里指**复用能力缺口**，不等于已发现功能错误。`TextScroll` 解决的是单行超宽文字的悬停滚动，不能代替列表的纵向滚动；场景框的 `UiTransform` 用于平移和缩放，也不等于带滚动范围与滚动条的列表视口。【源码核实：`kit/TextScroll.java:12-19`、`kit/UiTransform.java:7-52`】

现有 `UiNode` 只有文字/图标行、空白、分隔线及条件树专用的单层 `Frame`，`UiIcon.Sprite` 只表示固定尺寸的贴图区域，因此没有“缩略图打开全屏图片”的通用入口。【源码核实：`kit/UiNode.java:10-78`、`kit/UiIcon.java:26-38`】`OverlayLayer` 已能独占六类鼠标/键盘输入，但当前是考古笔记宿主内部的一次只开一个浮层机制；若未来给别的 Screen 使用，需定义宿主适配边界。【源码核实：`overlay/OverlayLayer.java:20-122`；后半句为设计推断】

## 二、目的

### 2.1 目标能力

1. 让考古笔记中的列表和弹层复用滚动、控件管理、tooltip、输入优先级与布局规则。
2. 降低新增面板时重复计算坐标和重复写鼠标事件的数量。
3. 保持现有场景树、书本布局及模态行为；每阶段选一个真实界面迁移，验证抽象是否有用。
4. 增加图片灯箱：从图片预览打开遮罩层，支持完整查看、缩放、拖动、关闭与可选图集导航，并与现有模态输入规则衔接。
5. 在考古笔记使用稳定后，让其他客户端 GUI 按需引用组件；预留面向第三方 Mod 的公开 API，并为未来独立库拆分控制依赖方向。**本计划不等于已经发布稳定 API 或独立库。**

### 2.2 架构目标

延续 `common` 客户端代码、不引入平台 API、服务端不引用客户端类的边界。使用 Java 描述内容与布局，由 Minecraft 原生绘制接口呈现。数据变化触发内容更新；平移、滚动和悬停不得导致全量节点重建。【依据：`docs/dev/internals/journal-ui-internals.md`「声明式 UI kit」】通用 kit 不依赖 `journal/`、考古笔记的状态、贴图、文案 key 或 `Constants.MOD_ID`；这些由宿主传入或留在适配层。这是未来拆包的依赖约束，不要求本轮新建 Gradle 子项目。【设计决策】

### 2.3 明确不做（本轮范围外）

- “类似网页灯箱”只指交互体验；不解析 HTML、CSS、JavaScript，不提供浏览器式 DOM 或通用动画系统。
- 不一次迁移整个考古笔记，不改现有服务端协议、业务判定或持久化格式。
- 不把 `OverlayLayer`、原生 `EditBox`、屏幕分页全部纳入 `UiDocument`。
- 不在首阶段实现任意深度嵌套容器、自动响应式断点或大列表虚拟化；若真实界面需要，再单独裁决。
- 灯箱首版只展示客户端资源管理器可解析的游戏资源与宿主提供的渲染源；不下载网页图片、不解析外部 URL、不访问任意文件路径，不引入图片上传或服务端同步。
- 不在本计划实施周期承诺二进制兼容、跨 Minecraft 版本兼容、Maven 发布或正式抽出独立库包；先形成可验证的公开边界，再另立发布计划。

## 三、技术原理

### 3.1 为什么先补滚动与控件组

场景选择和参数浮层已经有实际的列表、按钮与滚轮需求，却各自维护控件数组和命中循环。【源码核实：`panel/ScenarioSelectionOverlay.java:69-113,137-162`、`overlay/ScenarioParamsOverlay.java:68-134,153-224`】先在这些界面抽取共同契约，可以验证收益与输入语义。直接扩展 `UiNode` 为任意嵌套树会同时改变排版缓存、命中和 `Frame` 裁剪，首阶段风险更大。【推断：依据 `kit/UiNode.java:70-78`、`kit/UiDocument.java:91-149,324-349`】

### 3.2 为什么组合现有文档与控件

`UiDocument` 擅长连续内容与树行，`UiControl` 擅长固定边界的操作项，`OverlayLayer` 已负责模态占用输入。【源码核实：`kit/UiDocument.java:91-149,238-349`、`kit/UiControl.java:25-70`、`overlay/OverlayLayer.java:75-122`】第一轮以独立布局/滚动组件组合它们，可保留现有 `UiNode.Row` 的含义和单层 `Frame` 限制。横排、竖排若证明反复出现，再引入有界的组合布局；不把 `Row` 一词同时用于“文字行”和“容器”。【设计推断】

### 3.3 为什么保留宿主的输入入口

现有 `OverlayLayer` 会拦截打开模态时的六类输入，并保证上层绘制。【源码核实：`overlay/OverlayLayer.java:20-40,75-122`】新组件应返回“是否消费”或单一 `UiTarget`，由宿主沿既有屏幕入口调用。这样同一位置只能有一个 tooltip 来源，并能明确原生 `EditBox`、框角按钮和文档内容的优先级。【设计推断；现有优先级见 `panel/ScenarioFrameView.java:78-105`】

### 3.4 必须遵守的边界

- 坐标统一使用宿主 GUI 逻辑坐标；绘制、裁剪、命中、滚轮锚点必须经过相同变换。现有 scissor 与外部 pose 的约束见权威文档「声明式 UI kit」。【文档核实】
- `Frame` 仍只允许一层；首阶段的列表滚动不通过嵌套 `Frame` 实现。【源码核实：`kit/UiNode.java:70-78`】
- 节点、`Component` 与 action 仅在业务数据或尺寸变化时更新；稳定帧不构造列表、节点和 lambda。【文档核实：`docs/dev/internals/journal-ui-internals.md`「声明式 UI kit」】
- HUD/GUI 新文本使用本地化 key，并同时更新 `en_us.json`、`zh_cn.json`；取色经过现有语义色表。
- 无需新增 Mixin；若实施中发现必须新增，先依据事件 API 与项目 Mixin 规范重新评估。
- kit 的公开契约只依赖 Minecraft 客户端通用类型和自身 API；宿主数据、资源命名空间与 `OverlayLayer` 的具体实例通过适配器或参数注入。服务端加载路径不得链接 kit 类。【设计约束；模块边界依据 `docs/dev/foundation/architecture.md`「三模块划分」】
- 图片资源必须有已知的原始宽高或能由资源适配器读出；未找到贴图、尺寸非法、资源重载时须显示可理解的占位反馈并保持关闭操作可用。缩放及拖拽都必须钳制，不能让图片永久移出屏幕。【设计约束】

### 3.5 为什么将灯箱做成独立组件

`UiDocument` 目前按纵向块序列排版并只允许条件树专用 `Frame` 嵌一层；把全屏遮罩、键盘接管和图片缩放直接塞入 `UiNode` 会改变文档的排版及命中契约。【源码核实：`kit/UiNode.java:10-78`、`kit/UiDocument.java:91-149`；影响分析为推断】灯箱拟采用“可复用的图片视图 + 宿主模态适配器”：图片视图管理 fit/zoom/pan 与绘制命中，宿主决定用 `OverlayLayer` 或其他 Screen 层承载。这样既可在笔记中试用，也能由其他 GUI 复用。【设计决策】

### 3.6 为什么先划 API 边界再拆库

当前 `client/ui/kit/` 在 `common` 内，`UiKitDebugScreen` 还直接使用项目的 `Constants.MOD_ID` 与图标图集；现阶段它们都是工程内部代码。【源码核实：`kit/debug/UiKitDebugScreen.java:101-102`；模块位置见 `docs/dev/foundation/architecture.md`「三模块划分」】直接发布会把样例资源与业务宿主一起暴露为隐式依赖。计划先建立公开包与内部包的单向引用、最小接入示例和兼容规则，再做一次“只移动 kit 所需源码与资源”的拆包演练；演练通过后再决定正式发布方式。【设计决策】

## 四、技术路线

### 4.1 分层设计与目标结构

```text
宿主 Screen / OverlayLayer      输入入口、模态层高、持久化
  ├─ 考古笔记适配层              业务数据、贴图、文案、动作、原生 EditBox
  └─ kit 对外入口（拟议 api/）  宿主契约、组件配置、事件结果、灯箱请求
       └─ kit 内部实现           控件组、滚动、布局、焦点、图片视图、几何缓存
            ├─ UiControl / 原生 EditBox 适配
            └─ UiDocument         现有文字、图标和条件树内容
```

`UiDocument` 的块序列契约保持兼容。第一阶段新类型作为相邻组件，不要求业务方把所有页面改成一棵统一节点树。`api/` 是拟议的**公开包边界**，不是本次文档修改已经存在的目录；内部 `kit/` 类即使现在是 Java `public`，也不自动列为未来受兼容承诺的 API。

### 4.2 关键类型与 API 草案

以下仅定义行为边界；名称和方法签名须在首个迁移界面中验证后定稿。

| 拟议类型 | 最小职责 | 关键约束 |
|---|---|---|
| `UiControlGroup` | 按显式层序绘制控件、返回最上层命中目标和唯一 tooltip | 控件由宿主稳定持有；更新内容时按稳定 key 复用，不因滚动重建整个列表 |
| `UiScrollView` | 持有视口、内容高度、滚动偏移和滚动条命中；处理滚轮与拖动 | 偏移钳制到内容范围；内容变短、resize、语言切换后重新钳制；只绘制可见内容 |
| `UiLinearLayout`（第二阶段候选） | 纵向/横向排列，支持间距、内边距、固定尺寸与剩余尺寸 | 只做有限布局规则；先支持考古笔记真实需要的组合 |
| `UiControlStyle`（第三阶段候选） | 语义状态：普通、悬停、按下、禁用、选中 | 颜色从 `UiTextPalette` 及明确的背景语义取得，不在控件中散落常量 |
| `UiFocusManager`（第三阶段候选） | 可聚焦目标顺序、当前焦点、键盘激活与失焦通知 | 焦点范围由宿主或模态限制；与原生 `EditBox` 只接驳、不重做文字输入 |
| `UiImageView`（灯箱阶段） | 图片原始尺寸、等比适配、缩放、平移、裁剪与占位 | 不承担模态层序、不自行加载网络资源；资源重载后重新取图和尺寸 |
| `UiLightbox` / `LightboxRequest`（灯箱阶段） | 遮罩、标题/说明、关闭与可选前后图导航 | `UiImageView` 负责图片几何，宿主适配层负责打开/关闭与输入独占 |
| `UiHost` / `UiEventResult`（公开 API 草案） | 约定逻辑坐标、视口、绘制/输入转发、事件消费与焦点恢复 | 不把考古笔记的状态类、`OverlayLayer` 实例或平台事件类型写进签名 |

滚动容器需区分“内容高度”与“可视高度”，提供 `setViewport`、`setContentHeight`、`scrollBy`、`ensureVisible`、`hit`、`render` 等能力；确切签名由首个试点确定。滚动位置属于界面状态，是否持久化由宿主现有 `UiStateful` 机制决定，kit 不自行写盘。

### 4.3 功能优先级与行为契约

| 优先级 | 能力 | 首个使用点与验收行为 |
|---|---|---|
| P0 | 滚动视口与控件组 | 场景选择浮层：滚轮、拖拽/滚动条（若启用）、键盘选择、控件命中使用同一裁剪边界；内容缩短后偏移钳制 |
| P0 | 有界横纵布局、尺寸约束 | 参数浮层：固定、内容自适应与剩余空间三种尺寸规则；最小/最大值、内边距与间距；resize 后按钮和输入框不重叠 |
| P0 | 焦点与输入路由 | Tab / Shift+Tab 在可聚焦目标间移动，Enter/Space 激活适用控件，ESC 由模态宿主处理；禁用或不可见目标不进入焦点序列；拖拽捕获到释放为止 |
| P1 | 可访问性基础 | 焦点轮廓、键盘等价操作、文字/图标替代标签、可读 tooltip；在 Minecraft 可用的旁白入口补语义信息，不承诺完整屏幕阅读器能力 |
| P1 | 图片灯箱 | 缩略图打开、fit、滚轮/按钮缩放、按住拖动、复位、ESC/关闭按钮退出；缺失资源可退出并显示占位 |
| P1 | 语义样式与反馈 | 默认/悬停/按下/禁用/选中/焦点状态，使用主题 token；状态变化不要求重建内容树 |
| P2 | 图集与更多控件 | 灯箱前后图、键盘左右切换、页码；选择器、折叠组、进度/加载态等必须有真实第二个页面需求才排期 |
| P2 | 长列表优化与动效 | 只有测量表明需要时才引入虚拟列表或轻量过渡；动效尊重降低动态效果偏好（若宿主可提供） |

“更多功能”以通用布局、交互和可访问性为主线。每项功能需要至少一个真实页面验证；P2 是候选库，不等于本轮必做清单。焦点系统只管理 kit 所知控件和宿主注册的原生控件，原生控件仍由 Screen 处理编辑、剪贴板与 IME。

### 4.4 图片灯箱详细方案

| 场景 | 拟定行为 |
|---|---|
| 入口与数据 | 宿主传入一组 `LightboxImage`：稳定 ID、`ResourceLocation` 或受控绘制提供者、原始宽高、可本地化标题与描述；单图也是长度为一的组。只接受已在客户端可用的图片源。 |
| 初始显示 | 打开时以 `contain` 等比缩放，将整张图放入扣除控制栏与安全边距的视口；小图默认不主动放大，用户可手动缩放。居中并记录当前焦点用于关闭后恢复。 |
| 缩放与平移 | 滚轮在图片区域以指针为锚点缩放，`+`/`-` 按钮以视口中心缩放，提供“适应窗口”复位；按住主键拖动图片，放开结束。设明确的最小/最大缩放值与有限步进，resize 后重新钳制平移。 |
| 约束与裁剪 | 图片绘制严格裁剪到灯箱视口；若某轴尺寸小于视口，该轴居中并锁定平移，否则限制拖动到至少图片边缘仍与视口接触。命中、绘制与滚轮锚点共用坐标变换。 |
| 图集 | 有多图时显示上一张/下一张及“当前/总数”，左右键导航；切图重置为 fit，除非试用表明记忆每图缩放有价值。加载失败仍可切到其他图。 |
| 模态与关闭 | 遮罩覆盖宿主内容并吞掉下层输入；ESC 与可见关闭按钮可退出。是否点遮罩关闭由宿主配置，默认不关闭，以免拖拽误触；退出后恢复打开前焦点。 |
| 文本与反馈 | 标题、描述、按钮 tooltip、缺图/加载中状态由本地化 `Component` 提供；图标按钮必须有可供键盘焦点与旁白使用的名称。图片本身没有自动 OCR，替代描述由调用方提供。 |
| 生命周期 | 资源重载时丢弃尺寸/纹理派生缓存并重新求 fit；关闭释放输入捕获与引用。不得逐帧解码或创建新纹理。对超大纹理的限制按 Minecraft 资源管理器可接受范围处理，具体上限在实施时测量。 |

考古笔记首个灯箱入口拟选已有贴图说明或插图缩略图，具体素材由阶段开始时核实；不为验证灯箱而强行改变场景树的物品图标语义。若当前没有合适图片，先在开发调试页用项目已有贴图验收组件，再等待真实业务页面接入。外部 API 让调用方传图片列表和宿主适配器，不让灯箱直接引用笔记状态或固定资源命名空间。

### 4.5 对外 API 与未来拆包约束

拟议的公开入口按能力分组：`api.layout`（尺寸、视口、布局容器）、`api.input`（事件结果、焦点目标）、`api.component`（控件、图片视图）、`api.lightbox`（请求、图片描述、打开句柄）。名字只是设计占位，首个非笔记 GUI 接入时再定包名及签名。业务方只依赖这些入口；`UiDocument` 的内部排版缓存、`UiMetrics`、调试屏幕和笔记适配器保持内部实现。

公开 API 需写明：所有调用只在客户端主线程；坐标用 Screen 逻辑 GUI 坐标；尺寸变动与资源重载由宿主通知；对象所有权和 `close/dispose` 生命周期；事件消费与输入优先级；空值、非法尺寸和未知图片的处理。回调只返回语义动作，不直接持有 `Minecraft`、玩家状态或平台事件。可以使用 Minecraft 的 `Component`、`ResourceLocation`、`GuiGraphics` 等稳定于目标版本的客户端类型；这意味着未来独立库仍是 **Minecraft 1.21.1 客户端库**，不是脱离游戏的纯 Java UI 库。

拆包就绪门槛：① kit 实现不 import 项目业务包、资源常量及两端 loader API；② 开发调试示例移到示例/宿主适配层，资源由调用方提供；③ 新建最小第三方 Screen 示例只依赖公开包完成按钮、滚动与灯箱；④ 明确版本号、变更记录和兼容策略，区分实验性与稳定入口；⑤ 分离构建时验证 Fabric/NeoForge 都能消费同一库产物，且专用服务端不会加载客户端类。以上是未来独立库计划的验收条件，本次只记录，不执行拆包或发布。

### 4.6 数据与输入流

```text
业务数据或语言变化 → 内容 revision → 控件配置 / UiDocument 内容更新 → 必要时重排
resize             → 视口变化 → 必要时重排与钳制滚动偏移
鼠标与键盘          → Screen → OverlayLayer → 原生输入控件 / 控件组 / 滚动视口 / 文档
命中结果            → 唯一 UiTarget → 宿主执行 action 或绘制 tooltip
缩略图激活          → 宿主创建 LightboxRequest → 模态层打开 → 图片视图 fit/zoom/pan
灯箱退出/宿主卸载    → 释放输入捕获与资源引用 → 宿主恢复此前焦点
稳定帧              → 复用已排版几何与控件实例 → 绘制可见区域
```

输入顺序是宿主契约，不由各组件自行抢占：模态先于底层；模态内部原生输入框、悬浮按钮、列表内容按可视层序命中。滚轮只有指针位于相应视口时才消费；被模态接管后不得传给底层书页。

## 六、风险与限制

| 风险 | 说明 | 处置 |
|---|---|---|
| 坐标与裁剪不一致 | 书本外层缩放、滚动偏移、`Frame` 内缩放会叠加 | 统一坐标入口；先在 1x/2x GUI 缩放和场景放大框验证命中/裁剪；不新增旋转等变换 |
| 滚动输入穿透 | 列表未消费滚轮时可能让底层书页翻页 | 由 `OverlayLayer` 先接管；滚动视口只消费自身区域，宿主按返回值分发 |
| 重建开销 | 控件列表和 action 每次滚动重建会带来分配与文字测量 | 稳定 key 复用实例，分离内容、尺寸与偏移变化；使用现有 `UiMetrics` 对照 |
| 状态丢失 | resize、语言切换、内容收缩后偏移可能越界或归零 | 每次尺寸/内容变化钳制；恢复与持久化由宿主统一负责 |
| API 过早泛化 | 抽象多于实际使用点会增加维护成本 | 每类新组件至少由一个真实界面驱动，第二个使用点确认可复用性后再稳定接口 |
| i18n 与可读性 | 新控件状态或提示可能出现硬编码文本、低对比度 | 使用本地化 key 与语义色；保留超宽文本悬停滚动能力 |
| 焦点与原生输入冲突 | Tab、ESC、拖选或 IME 可能同时被 kit 和 `EditBox` 处理 | 宿主明确当前焦点拥有者；原生编辑期间由 `EditBox` 优先处理输入，模态切换时保存/恢复焦点并取消拖拽捕获 |
| 灯箱遮挡或无法退出 | 全屏遮罩可能盖住关闭按钮，资源加载失败时也可能卡在模态 | 关闭按钮始终绘于图片和遮罩之上；ESC 有独立退出路径；缺图走占位态并保留导航 |
| 图片几何失真与性能 | 贴图宽高、GUI 缩放和资源重载会影响 fit 与裁剪；逐帧解码产生卡顿 | 原始尺寸显式提供或缓存读取；同一变换用于画图/命中；只有资源变化才重建派生缓存，用调试计数检查 |
| 宿主假设泄漏到 API | `Constants.MOD_ID`、笔记状态、`OverlayLayer` 或平台事件进入公开签名后难以拆库 | 建立 import 方向检查和非笔记示例；公开签名只依赖目标 Minecraft 客户端类型与 kit 自身类型 |
| 跨版本兼容预期 | 第三方调用方可能把“预留 API”误读为稳定承诺 | 文档显式标注实验性、支持的 Minecraft/loader 范围与升级规则；正式发布另立计划 |

## 七、验证方式

### 7.1 编译与静态检查（开发执行）

每阶段完成代码后，优先通过 IDEA MCP 查工作区 Java 报错和警告（忽略 Markdown 格式提示），再执行 `./gradlew build`。Gradle 构建需等待至少 120 秒或直到任务明确结束，确认上一构建结束前不重复启动。无新增 `test` 文件；检查 `common/` 没有平台类 import、服务端路径没有客户端引用，两端客户端入口均可编译。

开发模式下利用 `UiKitDebugScreen` / `UiMetrics` 对照：静止帧不增加内容构建与布局计数；滚轮只改变偏移；resize 和语言切换可触发必要重排。若第三阶段加入调试边框，默认仅在开发开关启用时可见。灯箱阶段增加图片尺寸、fit 比例、缩放值、平移边界与当前焦点的调试读数；API 阶段检查公开包签名及 kit 内部 import 方向，并编译最小非笔记 Screen 示例。

### 7.2 实机验证（用户执行）

在 Fabric 与 NeoForge 分别检查：场景选择浮层的鼠标点击、滚轮、上下键、ESC、外部点击、tooltip；参数浮层的幸运值输入与拖选、确认/取消；窗口 resize、GUI 缩放、长名称与不同语言；打开模态时底层书页不响应输入。各阶段只验证实际修改覆盖的功能，后续测试由用户执行。

灯箱阶段按同一清单检查单图与多图（若启用）、鼠标和纯键盘两种路径：打开与关闭、缩放到上下界、拖到四个边界、复位、窗口/GUI 缩放、切语言、资源重载、缺图占位、关闭后焦点回到入口、打开时下层不得接受点击/滚轮/tooltip。可访问性阶段检查所有图标按钮有可读名称、焦点可见、Tab 顺序与显示顺序一致。API 阶段让示例 Screen 在两端运行，确认没有依赖笔记资源和状态。

**与计划的偏离**：

1. **验证方式**：开发用沙箱禁止 spawn 可执行文件（`java.exe` / `gradlew.bat` 报「拒绝访问」），因此本阶段未执行 `./gradlew build`，改用 IntelliJ MCP 的 `build_project` 与 `lint_files` 取证。**`./gradlew build` 与双端实机仍未执行，属待用户完成的验收项。**
2. **滚动视口的接入方式**：未采用「回调渲染内容」的形态，而是让宿主在 `push()` / `pop()` 之间自行绘制，并直接用 `toContentX` / `toContentY` 做命中。理由是与 `UiDocument` 现有的「变换 + 坐标换算」模型一致，且不需要逐帧回调对象。
3. **滚动条可见性**（原「八、待确认项」）：实现为**内容溢出才显示**，宽度 `UiScrollView.SCROLLBAR_WIDTH = 4`，宿主据此让出内容宽度；不溢出时 `isScrollbarVisible()` 恒为 false。
4. **焦点序列口径**：把「纯标签（`action == null`）不作为 Tab 停靠点」写进了 `UiControl` 契约。计划 4.3 只写了「禁用或不可见目标不进入焦点序列」，标签一项目为实施中补充。
5. **新增可见状态**：点击后控件保留 1px 焦点轮廓、按住时显示按下底色、边界箭头进入禁用态。第一项是 4.3「焦点可视反馈」的落点，但会改变旧画面，需实机裁决是否收敛（例如仅在键盘移焦时显示轮廓）。
6. **滚轮消费范围**：场景选择浮层只在指针位于滚动视口内时消费滚轮（依据 4.6「滚轮只有指针位于相应视口时才消费」）；面板内边距与底部箭头带不再响应滚轮。`OverlayLayer` 仍吞掉全部输入，故底层书页不会翻页。

**独立验证结论**（只读验证者，2026-09-27）：通过 10 项、不通过 5 项。其中 4 项已修复——滚动条「点轨道跳转后抓取偏移取样过早，导致下一次拖动把滑块拉回原处」（真缺陷）、纯标签按住显示按下底色、`UiLinearLayout` 的 `REMAIN` 未预扣 min、拖动后箭头禁用态最长 1 秒陈旧。1 项保留并记录：样本档位 ≥82 时样本格宽退化为 0（旧实现在同参数下会抛异常，新实现不再崩溃但该档位不可用；实际档位为个位数，判定不可达）。

复验（同一只读验证者）确认 4 处修复全部成立（含手算推演：轨道跳转后不再回退、拖动 1:1 跟手、`travel == 0` 无除零、纯标签不再有按下底色且防穿透保持、混合 min 的 `REMAIN` 从越界变为恰好填满、改偏移的 6 条路径都刷新箭头禁用态），两处降噪改动无语义风险。按复验建议又收敛了 3 处：抓取偏移改用未取整的滑块位置（消除跳转后第一个拖动事件的像素对齐残留）、`configure` 移除动作时同步清 `pressed`、`UiLinearLayout` 的一处注释口径与新实现对齐。最终全项目 `build_project` 仍为 `isSuccess=true / problems=[]`，`lint_files` 为 0 error。

**已知未覆盖项**（不构成本阶段交付，留待阶段 C/D）：

4. **fit 的时机写进了内容契约**：`Content.contentWidth()` 允许返回 0；返回 0 时外壳把 fit 延后到尺寸就绪那一帧。这是条件树路径的必要条件（文档内容要到 render 阶段才装入，空文档宽度为 0，直接 fit 会误选最大档位）。
5. **放不下时不居中**：适应窗口在「哪个档位都放不下」时保留内容左上角（pan = 0），只保证拖动不露出内容边界外的空白。理由是条件树从根部往下读，左上角是合适起点；与 4.4 只要求「限制拖动到边缘仍与视口接触」一致。
6. **调试页复用生产模态路径**：调试页用 `OverlayLayer` + `LightboxOverlay` 承载灯箱，而不是手写遮罩与输入独占，因此调试页同时验证了生产接入方式。

**独立验证结论**（只读验证者，2026-09-27）：通过 8 组、不通过 2 项、提示 5 项。两项已修复——① **条件树灯箱打开即 300%**（fit 在内容尺寸未知时决策，误选最大档位；已在内容契约与外壳里改为延后 fit）；② 适应窗口在放不下时的行为与注释矛盾（选择修正注释、保留左上角起点）。五项提示中三项已收敛：页码读数改为按 index/total 缓存、`onClosed()` 补上结束内容拖动、控制栏过窄时不画读数以免重叠。验证者手算确认：指针锚点缩放两组用例精确不动、图集单图隐藏导航、两份 lang 键集合完全一致（各 884 键）、调试页模态独占与未缩放拖动增量均成立。

**已知未覆盖项**：

- **资源重载只做了一半**：项目里没有跨平台的客户端资源重载监听，因此 `UiLightbox.invalidateResources()` 仍没有宿主调用方。补偿措施是 `UiImageView` 在**缺图状态**下按约 1 秒限频重查资源，因此「先缺后补」的贴图无需宿主接线也能自愈；但「贴图在打开期间被移除/替换」仍需宿主调用 `invalidateResources()` 才会被发现。
- **「受控绘制提供者」入口未实现**：`LightboxImage` 只接受贴图区域；需要动态绘制时走 `UiLightbox.Content`（条件树就是这么做的），但没有独立的 draw-provider 描述类型。
- **超大纹理上限与降采样未实现**：8.0 倍缩放由 GPU 完成，没有尺寸上限或降采样处理（计划要求在实施时测量，尚未测量）。
- **「加载中状态」未实现**：只有「缺图占位」；本地贴图场景下可视为不适用。
### 9.5 阶段 E（公开边界、示例层、兼容策略）+ 焦点回交 bug 修复——2026-09-27

**用户实测 bug**：点击场景页条件树的放大按钮、关闭灯箱后，焦点轮廓仍留在放大按钮上。根因是 `OverlayLayer.open` **无条件**把 opener 登记为返回焦点，而设计上鼠标点击根本不夺取焦点——鼠标打开的浮层关闭时却把焦点「恢复」到了从未聚焦过的按钮上。修复：

| 位置 | 变化 |
|---|---|
| `ui/kit/UiFocusTarget.java` | 新增 `isFocused()`：目标必须能回答「我现在是否持有焦点」 |
| `ui/overlay/OverlayLayer.java` | `open(...)` 只在 `opener.isFocused()` 为真时登记返回焦点（键盘路径仍恢复，鼠标路径不再留下轮廓） |
| 三个宿主 + 灯箱 + 示例页 | 鼠标按下即 `clearFocus()`：点击被消费后不再保留键盘焦点轮廓 |
| `ui/sample/UiKitSampleScreen.java` | 把灯箱按钮作为 opener 传入，并在未被子层消费的点击里 `clearRestoredFocus()` + `focus.clearFocus()`，让「返回焦点」契约有活路径与回归覆盖 |
