### 1.2 核心矛盾：结果身份不能代表生成过程

当前两条数据流相互分离：

```text
静态 JSON → 函数处理器 → 预览栈 / 签名 / 提示
运行时表 → 模拟最终 ItemStack → 签名匹配 → 出现概率
```

例：路径 A 固定掉 2 个钻石，路径 B 随机掉 1～3 个钻石。两条路径都可能得到完全相同的 `ItemStack`，即使比较物品、组件和数量，也无法从结果唯一反推函数。不同附魔规则还会被主动合并为同一个 `ENCHANTED_APPROX`。

这是信息丢失问题，不是提高 `LootResultMatcher` 比较精度就能解决。应分别表达：结果签名、静态获取规则、本次模拟实际观察到的函数。**同一结果允许对应多条函数链。**

## 二、目的

### 2.1 可达目标与验收含义

| 层次 | 目标 | 达到什么程度即算完成 |
|---|---|---|
| 静态规则 | 补齐高价值字段，并保留函数条件、顺序与包装关系 | 未模拟时也能解释“这条路径声明了什么”；不把抽样范围冒充声明范围 |
| 模拟观测 | 将捕获到的函数执行关联到最终产物 | 可以说“本输入的模拟中，这个结果曾经过这些函数”，不要求定位到原始 JSON 的某个 entry |
| 多来源结果 | 同签名保留多条观测链 | 不把 A/B 两种备选生成方式拼成一次顺序执行；重复捕获不无限增加文案 |
| 语义修复 | 数量附魔、函数条件与掉落条件正确分离 | 未触发数量修改仍可掉落；数量函数不再凭空制造附魔书/附魔签名 |
| 平台注入 | 已确认的平台注入来源统一显示“模组联动” | 不要求知道具体第三方函数、修改器类、内部条件或函数顺序 |
| 降级 | 不能解析、未捕获、超限、来源未知各自可解释 | 不猜测、不误标注；基础模拟与概率统计仍可继续 |
| 一致性 | 新算、缓存恢复、换输入、重载后的说明一致 | 观测绑定表哈希和输入键，不串场景，不用别的输入的记录证明当前输入执行过 |

### 2.2 架构目标

1. 静态函数描述为规则权威；运行时观测为执行事实，二者共同进入现有目录派生和展示链路。
2. 保留现有物品进度签名体系；函数描述、观测链及来源状态不并入签名存储键。
3. 默认新增两个 common 捕获入口：条件函数实际执行、战利品局部拆栈；业务逻辑放普通类。
4. 不建立完整的运行时表对象图，不以运行时对象到 JSON 节点的一一映射为前置条件。
5. 不要求新建专门页面；优先扩展已有物品 tooltip 与场景分支内容，沿用统一 DTO/codec。

### 2.3 明确不做（本轮范围外）

- 不保证精确定位运行时 table/pool/entry 索引、同一子表的不同调用位置或源码行；不新增仅用于这些定位的 entry/pool Mixin。
- 不为每个函数计算独立概率，不统计逐函数前后完整物品差异，不输出全部抽样流水。
- 不逐个适配第三方 `LootItemFunction`、任意自定义 Consumer 或自定义 `ItemStack` 复制路径。
- 不深挖第三方 GLM 管理器、不恢复其完整函数链、不根据物品 namespace 猜提供者。
- 不将容器内容作为外层战利品统计，不递归触发 `set_loot_table` 指定的未来开箱过程。
- 不全面重写原版战利品执行器、不替换 `compose` 循环、不将所有随机结果静态枚举成新签名。
- 不清除玩家笔记进度，不自动把旧附魔进度键批量改成普通物品键。
- 本文编写阶段不执行以上代码修改；实施需按下面阶段推进。

## 三、技术原理

### 3.1 选择执行观测，不从最终结果反推函数

**证据等级：源码核实 + 推算。** `LootResultMatcher` 只比较最终结果与候选签名；不同函数可得到同一结果，因而逆向映射不是唯一的。捕获必须发生在执行期间，结果归类仍使用已有签名。

本轮收窄为“最终结果 ↔ 已观测函数链”，不强求“最终结果 ↔ 唯一静态获取路径”。静态路径上的函数与模拟观测分别展示；不通过描述相同或 hash 相同来宣布它们来自同一位置。

### 3.2 优先捕获条件通过后的 run，不只监听 apply 返回

**证据等级：源码核实。** `V:functions/LootItemConditionalFunction.java:36`：

```java
return compositePredicates.test(context) ? run(stack, context) : stack;
```

本地原版 40 个注册函数中，39 个继承此基类，`SequenceFunction` 单独实现 `LootItemFunction`。在 `apply(ItemStack, LootContext)` 内包住 `run` 调用，能复用原版条件判定且同时取得函数对象、输入栈、返回栈。项目已有 `NestedLootTableMixin` 的 MixinExtras `@WrapOperation` 用法。

- 本记录的语义严格为“外层条件通过并进入函数执行体”，不宣称物品实际发生变化。
- 只监听 `apply` 返回无法区分条件失败；重新执行 `conditions.test` 会改变随机序列，禁止采用。
- `filtered` 内部仍可能过滤失败；只观测到外壳时不能宣称内层 modifier 已执行。
- `sequence` 的叶子函数会正常经过公共入口；首轮无需为无副作用的序列外壳增加 Mixin。
- 第三方直接实现接口或绕过此基类时不保证捕获，必须保留“记录可能不完整”。

### 3.3 用对象身份维持本轮来源，不污染物品数据

**证据等级：源码核实 + 设计推算。** 附魔书转换等函数返回新对象；`V:LootTable.java:61` 的拆栈器可能继续复制最终栈。需要在局部捕获点显式传递来源。

采用 `IdentityHashMap<ItemStack, TraceHandle>` 作为模拟作用域内的旁路数据。函数返回新对象时继承已知链；拆栈时为输出副本继承链；所有记录最终按结果签名聚合。禁止写入追踪组件/NBT，避免干扰物品比较、堆叠和其他函数。

禁止使用“相同物品+相同组件”的回退作为函数链确定归因。对象关系断裂时标记未完整捕获，不能任取一个相似栈的来源。现有子表统计可继续沿用原有契约，但其模糊回退不得提升为函数链证据。

### 3.4 静态描述和运行时对象不做强制一一映射

**证据等级：源码核实 + 设计选择。** 投影器重新解码的函数对象不是运行时注册表内的同一对象；`FunctionReference.run` 会通过 resolver 获取 modifier（`V:functions/FunctionReference.java:61`），说明“纯静态编译层取不到”不等于“运行时永远无法获取”。

更轻的路线是：捕获实际函数对象后，按实例缓存注册类型和可取得的参数描述，复用静态函数描述器；能通过原版 Codec 与正确的 lookup 编码就编码一次，不能编码则仅保留类型和解析等级。不读取任意第三方私有字段，不新建全量对象图来定位 JSON。

结构相同可以用于**展示内容去重**，不能用于证明相同调用位置。`reference` 静态侧优先保留引用名；有可用的正确注册表视图时有界展开，否则部分解析即可，不因此扩大编译层依赖。

### 3.5 保留平台最终结果，平台注入不要求函数解释

**证据等级：字节码核实（IDEA 反编译）+ 源码核实。** `N:LootTable#getRandomItems(LootContext)` 先生成并拆栈，再调用 `CommonHooks.modifyLoot`；项目模拟器之后还调用 `ArchaeologyLootInjectors.maybeReplace`。

必须继续走普通 `getRandomItems`，不得为了简化捕获改用根表 `getRandomItemsRaw` 而漏掉 GLM。已确认平台来源统一标为“模组联动”；可复用已有声明条件，但不扩展为第三方内部函数解析。

“没有静态候选”“没有观测链”“物品来自 mod 命名空间”都不是注入证据。无法确认来源的动态结果保留为运行时来源未知，避免把原版熔炼结果误标成模组联动。

### 3.6 必须遵守的边界

- 捕获作用域之外原逻辑执行一次；作用域内也执行一次，不重掷条件、数值提供器或函数。
- Mixin 只转交参数与返回值；记录失败可降级，原战利品执行异常不得吞掉或重新调用原函数。
- 一个输入的观测不代表全部条件和全部可能结果；没有记录不代表没有函数或函数不可能执行。
- 函数条件和产物出现条件分开；数量改为零、物品变换等仍可能影响最终产出，不能反向概括为“所有函数条件都与掉落无关”。
- common 不依赖平台类；服务端不依赖客户端；i18n 同步双语；先确认现有 Event API 是否足够，事件粒度不足时才保留窄 Mixin。
- 现有概率口径为每轮至少出现一次，同一轮多路径和拆栈不得重复加概率；捕获不得另起计数权威。

## 四、技术路线

### 4.1 目标结构与数据流

```text
静态资源 → 编译/投影 → 函数描述树 → 获取路径规则 ───────────┐
                                                        │
普通 getRandomItems                                     │
  ├─ 条件函数 run → 本轮对象身份关联 → 函数输入/输出传递    │
  ├─ 局部拆栈 → 各输出继承追踪记录                        │
  └─ 平台后处理 / 显式注入 → 最终 drops                   │
                               ↓                        │
                    签名匹配及既有每轮计数                │
                               ↓                        │
                   输入级函数观测摘要 + 来源状态          │
                               ↓                        │
                     SimulationMeasurement / 缓存       │
                               └──────────────→ deriveTable
                                                        ↓
                                      DTO / codec → tooltip / 场景分支
```

静态说明挂在获取路径上；观测摘要挂在“表哈希 + 输入键 + 结果签名”上。**不增加连接它们所必需的运行时 PathId，也不强行把观测写回某条静态路径。**

### 4.2 数据模型草案

以下为职责/API 草案，不是已存在类型或必须原样照搬的声明。实施时优先复用同义值类型，避免重复枚举。

| 类型/字段 | 最小职责 | 不变量 |
|---|---|---|
| `LootFunctionInfo` | 函数类型、类型化参数、函数自己的条件、子函数、描述保真度 | 不包含实际执行次数，不修改结果签名 |
| `FunctionFidelity` | 完整描述 / 部分描述 / 未解析 | 描述完整不代表执行捕获完整；动态数值是合法描述，不自动等于解析失败 |
| `FunctionEffectKind` | 数量、物品变换、组件、包装、容器、未知 | 用于预览与条件语义处理；不能只用一个 `addsRandomness` 表达全部情况 |
| `LootAcquisitionPath.functions` | 本路径声明的有序函数树/链 | 纳入路径相等性和去重，避免条件相同、函数不同的两条路径被合并丢失 |
| `FunctionTraceSession` | 本输入的有界函数字典、链字典、聚合摘要 | 不暴露全局静态强引用；目录重载/任务结束后可释放 |
| `TraceHandle` / `TraceNode` | 本轮栈的既有函数链及包装层次 | 顺序和重复次数有意义；多条备选链分别保存 |
| `ObservedFunctionChain` | 有序函数引用、已知包装关系、捕获状态 | 不携带猜测的 table/pool/entry 位置；不宣称每个函数改变了物品 |
| `FunctionObservationSummary` | 当前输入当前结果的去重链列表、截断/未完整捕获状态 | 明确区分未观测、已观测到部分执行、超限截断；空列表不是“无函数”的证明 |
| `LootOriginKind` | 普通静态来源、确认的模组联动、运行时来源未知 | 支持同结果同时有普通来源与模组联动；不能只有互斥的单个条目布尔值 |

参数优先用明确结构表达：注册 ID、常量、静态范围、动态数值表达式、布尔、槽位等。复用条件侧保真度约定，但不把函数伪装成 `LootConditionInfo`，也不存放无限制任意 JSON。

只保留一个结构化函数描述来源；旧 `tooltipHint` 改为由结构化描述派生的兼容摘要，不能继续维护第二套独立参数拼接逻辑。既有 `injected` 可作为兼容派生字段，新增来源集合承担真实语义。

### 4.3 静态描述与语义修复

**描述与预览独立。** 每个函数先生成 `LootFunctionInfo`，再尝试静态预览；预览成功也保留描述。附魔签名可以继续折叠，提示不再被通用“附魔”覆盖。

**函数条件原位保存。** 从 `resolvedConditions` 移出函数内部条件，记录到对应函数节点。预览只在能证明执行条件和效果时静态应用；否则保留条件效果说明及不确定性。对只改数量/组件的可选效果，不再把条件失败当成基础物品不可获得。

**条件变换保守处理。** `set_item`、附魔书转换等若有条件，可能存在多个输出。仅对容易确定的基础/变换结果保留备选，不全面枚举条件组合。无法静态确定时展示“产物需模拟确认”，动态发现的实际输出承接观测链；不能保留一个错误原物品条目并声称它是确定产物。已有静态近似占位要显式标识为规则预览，不能与已观测产物混淆。

**实际命中不可被错误静态假设抹除。** 审查 `simulateRoll` 的 `rawMatched → continue` 以及场景适用签名筛选；修复函数条件后，用有条件数量函数及物品变换验证。若剩余模型不足导致实际输出被排除，应保留观测事实并降级路径解释，不能把已产生的物品算成零或静态不可达。

### 4.5 模拟执行捕获

#### 4.5.1 作用域、调用与对象传递

复用 `LootSimulationScope` 的生命周期，向其中挂接本次任务的 `FunctionTraceSession`。每个时间片开启作用域，每轮清空栈关联；任务聚合数据留在 job 中，不依赖上一个时间片的 `ThreadLocal`。

公共入口的普通 Java helper 按以下职责处理：

1. 无活动捕获上下文时透传原调用，不创建追踪对象。
2. 有上下文时读取输入栈现有链，为当前函数建立执行帧，原调用仅执行一次。
3. 正常返回后，将前置链、当前执行节点和已观察到的同物品内层调用关联到输出对象；必要时传递到新对象。
4. 异常时用 `finally` 退出帧；原执行异常继续传播到既有模拟失败处理，不重试函数。
5. `ItemStack.EMPTY`、空栈及未被输出消费的栈，不作为最终产物记录；不能以共享 EMPTY 为不同来源建立公共关联。

物品在原地修改时不依赖其 hash；记录关联使用对象身份。运行时注册类型/参数描述按唯一函数对象缓存，昂贵的 Codec 编码和本地化拼装放到可计入预算的摘要处理处，不写进 Mixin 热路径。

#### 4.5.2 包装、顺序与容器隔离

- 普通函数按实际执行顺序组成链，连续两个相同类型函数不折叠成一次执行。
- `filtered`、`reference` 的执行帧保留父子关系，内层返回新栈也要向外传播；不要在内层已记录后再平铺重复追加相同节点。
- `sequence` 以叶子执行顺序表现。未执行的叶子不进入观测，静态描述仍保留整条规则。
- 对 `set_contents`、`modify_contents`，进入执行帧时暂停对子内容的详细采集，退出后恢复；容器本身的包装节点可记录为“内容未展开”。其间不能把子内容的函数串到外层容器上。
- 同一轮多件物品不共用一份可变函数列表；链节点/列表使用不可变共享或复制，防止后续函数污染已经输出的兄弟物品。

#### 4.5.3 局部拆栈入口

优先在 `LootTable.createStackSplitter` 的实现内，包装 `ItemStack.copyWithCount` 调用，将输入追踪关系传给副本。Mixin 业务仍只转交普通 helper。

该调用位于编译器生成的 lambda 中，**准确目标方法名、描述符及两平台 remap 必须在实施时确认**，不能把本地反编译参数名或 lambda 序号当稳定 API。若窄调用点在目标平台不可维护，可采用保留原 splitter、包装其输入/输出 Consumer 的替代方案；同样不得重写拆栈算法。

两种方案只选一种，不叠加重复记录。禁止对 `ItemStack.copy`、`copyWithCount` 全局注入来追踪所有游戏物品。第三方自行复制、合并或替换的输出不保证延续来源。

#### 4.5.4 收集位置与最小闭环

模拟器取得**平台处理后的最终 drops** 后，先取可用的观测句柄，再沿既有逻辑确定结果签名。在“已有候选命中”“动态签名创建”等全部计入结果的路径上统一聚合摘要，避免被早退的 `continue` 漏掉；不能只记录动态发现条目。

首轮两个 common Mixin 即构成主要捕获闭环：`LootItemConditionalFunction` 的 `run` 调用与 `LootTable` 的局部拆栈。不新增路径定位 Mixin。平台自身代码若有明确的替换/注入位置，可调用普通 helper 清除失效链并声明“模组联动”；第三方后处理无可靠关系时只保留已知观测片段，不宣称它描述了完整最终生成过程。

### 4.6 平台注入与来源展示

复用当前 `DeclaredLootInjection`、`Services.PLATFORM.describeLootInjections`、`RuntimeLootLinks` 和既有平台适配代码。不要另造一份注入规则库。

| 来源证据 | 展示及处置 |
|---|---|
| 已有适配器明确声明注入规则，或自有注入执行点明确标记 | “模组联动”；可保留现有可信条件和追加/替换含义，不要求函数链 |
| 普通路径与注入路径产出同签名 | 条目下并列普通规则与“模组联动”；不能把普通来源说明整体覆盖 |
| 原版捕获链可证明发生物品变换，产生静态候选外结果 | 展示动态结果及捕获片段，不因其动态发现而标“模组联动” |
| 第三方新增结果或替换后身份丢失，现有平台接口无法确认 | 显示“运行时来源未解析”，不猜具体 mod；未能识别为注入是已接受限制 |
| 已有声明只说明某物可能被注入，无法区分本次同名产物 | 声明作为一条可能来源展示，不能宣称本次每个同签名样本都由注入产生 |

本轮不增加通用第三方 GLM 追踪 Mixin，不做最终列表的全组件差分来恢复每个修改器的操作。用户要求的“模组联动”是**对确认注入的简化解释**，不是给所有未知来源贴同一标签。

已有 `injected_loot` 本地化 key 直接复用；内部可以保留现有可信提供者信息供诊断，但玩家界面统一名称，不新增修改器类名等技术字段。

### 4.7 性能、容量与失败降级

- 热路径只做活动作用域判断、对象身份查询、紧凑节点关联；不逐次解析 JSON、反射字段、构建本地化 Component 或复制完整物品栈。
- 描述按函数实例缓存，执行链按结构去重；每输入每结果仅保留唯一链集合，不保留每轮日志。重复调用次数在链中保留，重复抽样记录不重复存储。
- 初始容量建议：每条链最多 64 个节点、嵌套深度 16、每结果最多 16 条观测链、每输入最多 4096 个唯一描述/链条目。它们是实施起始预算，不是已测性能结论；根据用户实机指标调整，不能静默截断。
- 上限必须同时约束函数实例缓存、本轮栈关联和待处理描述队列，不能只限制最终输出。初始建议每轮最多关联 4096 个栈对象；达到上限后暂停该轮新增捕获并标记截断，仍完整消费最终 drops 和进行概率计数。动态函数实例也不能绕过描述总预算无限留存。
- 单输入运行时观测的编码总量建议设 256 KiB 上限，并同时遵守现有目录分片/网络包的更小上限；截断只裁观测详情，不删物品条目、不改概率。静态描述、引用展开、文本长度和客户端解码也需有界。
- 达到上限时写入明确截断标志，停止增加详细记录，基础掉落模拟继续执行。解析失败按类型去重诊断，不逐物品刷日志。
- 记录器自有异常降级为“观测不可用”；原函数异常按原有模拟失败规则处理。两类异常必须在代码结构上分开，避免把实际战利品异常吞掉。
- 时间片提前返回、任务失败、数据包重载均释放作用域；按代次校验结果，旧任务不能向新目录提交描述。
- 使用现有 `LootSimulationMetrics` 增加捕获耗时、唯一链数、截断数；不虚构“零开销”。

### 4.8 缓存、同步和展示

**缓存层次**：静态描述由当前资源/注册表投影产生；本输入函数观测进入 `InputMeasurement`，随该输入测量缓存被 LRU 淘汰。表级 `discovery` 继续保留动态物品存在性与来源类别，不因观测摘要淘汰而删除物品。不能把跨输入汇总的观测冒充当前输入事实。

**版本与依赖**：当前 `FORMAT_VERSION=4`、`SIMULATION_CACHE_VERSION=loot-analysis-v21`；实施时读取最新值并递增，旧测量按缓存未命中处理，不迁移旧数值。函数描述规则版本、静态函数结构、被展开的 item modifier、相关 tag/附魔定义以及新增依赖必须纳入失效口径。熔炼等运行时外部依赖若无法可靠形成摘要，采用重载代次/会话盐让受影响的输入重算，牺牲命中率；不能继续承诺持久缓存完全有效。只影响展示的数据也要让目录 hash/同步内容发生相应变化。

**玩家进度**：不新增签名枚举和函数参数进度键。`enchanted_count_increase` 修正会改变错误预览产生的候选集合；历史同名附魔键可能也来自真实附魔路径，不能批量转换。保留既有进度，消失的错误候选按原有孤儿键口径处理，并列入用户回归检查。

**同步**：扩展 `CatalogTableDto` 和唯一 `CatalogStreamCodec`，全量目录、按需结果共用编解码。只传有界结构化摘要及本地化参数，不传 `LootItemFunction`、`LootContext`、`ItemStack` 对象身份或完整原始 JSON。网络结构随同版本客户端/服务端一起发布。

**捕获状态**：本轮不默认发布“完整生成过程已捕获”状态。即使已知原版函数片段都被记录，平台后处理仍可能存在不可见行为；界面使用“观测到的函数”及必要的未展开/截断说明。规则描述的完整度与执行链完整度分别存储、分别解释。

**展示**：每条静态路径展示“生成规则”；当前输入有观测时展示“本次模拟观测到的函数”。观测中多个链使用备选分组，不能用逗号拼成一个因果链。附魔通用摘要可以保留，但不能覆盖参数。无观测、部分捕获、未解析函数、截断各有简短提示；“进入执行体”不写成“必然生效”。

**与当前分支 UI 衔接**：`ScenarioBranchCatalog` 当前根据获取条件生成分支；新增函数条件不得再进入它的主门槛。静态函数可随分支展示，运行时观测留在结果说明中，不分配到某一分支。保留未命中分支的静态描述，不因为本次没观测而删除规则。

## 五、决策记录

| 编号 | 决策点 | 结论与理由 |
|---|---|---|
| D01 | 结果身份与来源 | 结果签名继续用于计数/进度；静态规则、运行时观测另存，不因函数参数拆分进度 |
| D02 | 精确运行时位置映射 | **放弃作为本轮目标**。不建全量运行时对象图，不要求 JSON 位置一一对应；复杂度与收益不匹配 |
| D03 | 运行时对象描述 | 仅做按实例缓存的类型/参数提取；Codec 不可用时保留类型与降级，不任意反射第三方实现 |
| D04 | Mixin 入口 | 首选公共 `apply` 内的 `run` 调用，加局部拆栈传递；不在每个原版函数写一个 Mixin |
| D05 | `compose` 方案 | 不重写组合器；它有空链/单函数优化，包装构建发生在模拟之前，且内部直接调用仍需处理 |
| D06 | `decorate` 单入口方案 | 不作为逐函数捕获方案；只能观察组合输入输出，无法自然区分内部条件通过与否 |
| D07 | 同名/同组件反推 | 不作确定归因。结构内容相同只可去重描述，不能认定相同路径 |
| D08 | 平台注入 | 确认来源后统一“模组联动”，复用已有声明；不新增第三方 GLM 内部追踪器 |
| D09 | 动态结果 | 动态发现不等于平台注入；来源未知单列，避免把原版变换误标 |
| D10 | 条件语义 | 函数内部条件与物品生成条件分开；有条件的身份变换保守处理，不全量展开组合 |
| D11 | `sequence` 与容器 | 序列捕获叶子即可；容器子内容运行时不展开，避免跨物品串链 |
| D12 | 观测完整性 | 记录表示进入执行体，不保证改变结果、不保证捕获全程；未知、部分、截断明确区分 |
| D13 | 存储口径 | 观测属于输入级测量缓存；动态条目存在性属于表级 discovery，不因观测淘汰而消失 |
| D14 | 捕获性能 | 有界字典与链聚合；不复制每步完整栈、不输出逐轮日志、不声称零开销 |
| D15 | 修正先前结论：附魔提示 | 不是附魔签名使所有 `describeHint` 调用被跳过，而是调用条件受限且最终汇总会覆盖提示；两处都需解耦 |
| D16 | 修正先前结论：数量附魔 | `enchanted_count_increase` 不给产物附魔；从附魔产物分类移除 |
| D17 | 修正先前结论：确定性 | `set_enchantments` 支持动态等级；熔炼也依赖实际输入和当前配方，不应无条件宣称完全静态确定 |
| D18 | 修正先前结论：容器引用 | `set_loot_table` 延迟生成，容器内容不等于外层掉落；不作为普通引用图边直接展开统计 |
| D19 | 修正先前建议：完整来源追踪 | 上轮讨论的 table/pool/entry 全路径追踪降为范围外，改为结果级执行观测；减少注入点和运行时索引成本 |
| D20 | 缓存版本依据 | 以本轮源码 v21/格式 4 为基线，实施时再读取最新值，不复制旧文档的版本数字 |

## 六、风险与限制

| 类型 | 风险/限制 | 处置 |
|---|---|---|
| 已知限制 | 一个结果可来自多个静态路径，运行时没有精确位置映射 | 分开展示规则和观测；不提供逐路径实测概率或唯一归属 |
| 已知限制 | 第三方直接实现函数接口、自定义复制/合并可能绕过捕获 | 只承诺原版公共链路；保留片段，标注未完整捕获，不逐类补 Mixin |
| 已知限制 | GLM 可能原地修改同一对象，使捕获链只是最终结果的前置片段 | 不把片段宣称为完整生成解释；确认注入时用模组联动，未知时不推断 |
| 已知限制 | 第三方平台注入不一定能被现有接口识别 | 未确认来源保留未知；全面识别不是本轮完成条件 |
| 已知限制 | 容器内容、未执行函数、未命中分支没有完整运行时记录 | 静态规则补充，容器内容不展开；无记录不等于无规则 |
| 已知限制 | 历史错误附魔签名与真实附魔签名可能重合 | 不批量迁移或删除进度；说明候选修正后的孤儿键表现 |
| 已知限制 | 完整规则可能很长，观测链数量可能增长 | 容量/字节预算及显式截断；不影响基础统计 |
| 待验证假设 | lambda 中的 splitter 窄注入可在两平台稳定 remap | P0 核对目标；不稳定时采用保留原 Consumer 的包装方案，仍不全局注入 ItemStack |
| 待验证假设 | 小量对象关联与链去重的性能可接受 | 使用现有 metrics 对比；超出预算先减少观测细节，不降低抽样次数来掩盖开销 |
| 待验证假设 | 提取运行时函数参数时正确的 RegistryOps 能覆盖主要原版类型 | 以实际 lookup/Codec 结果为准，失败按类型降级，不阻断掉落 |
| 待验证假设 | 外部依赖摘要能覆盖 modifier/tag/配方变化 | 覆盖不了的受影响缓存禁用跨代复用，采用会话/重载盐；不沿用过期说明 |

## 七、验证方式

### 7.1 本轮规划文档检查

只核对文档结构、源码依据、当前版本、用户已确定的取舍与范围边界；本轮仅新增 Markdown，按项目规则不运行格式校验、IDEA 代码检查或 Gradle 构建。

### 7.2 编译验证（实施开发执行）

1. 先通过 IDEA MCP 检查 git 工作区改动文件的报错/警告，忽略 Markdown 格式问题；修复明确问题后再构建。
2. 执行一次 `./gradlew build`（Windows 使用对应 wrapper），持续等待到结束。构建总等待预算至少 120 秒；工具单次等待上限较短时分段等待同一任务并更新进展，不启动第二个并发构建。
3. 核对 Fabric remap、NeoForge/common 编译与打包、Mixin 配置、客户端/服务端隔离、DTO 构造与双语 key 同步。编译成功不替代游戏启动时的 Mixin 应用验证。
4. 不新增 `test` 文件；实机测试交由用户。失败原因不明或需要扩大设计时停止并说明，不把运行时验证缺失写成通过。

### 7.3 实机验证（用户执行）

实施交付时提供以下最小复现场景的操作与预期；可用临时数据包构造样例，需在测试世界运行，不作为生产数据永久保留。开发侧准备样例不等于代替用户启动测试。

| 场景 | 预期 |
|---|---|
| 同物品：固定数量 2 与随机数量 1～3 两条路径 | 一个结果条目可有两种规则/观测链，不反推唯一来源，不将两链串成叠加 |
| 条件失败的 `set_count` | 基础物品仍可被计入；该数量函数不出现在“已进入执行体”的观测里 |
| `enchanted_count_increase` 应用于普通物品/书 | 只改变数量及说明，不凭空成为附魔产物；上下文不满足时仍可保留基础掉落 |
| `set_enchantments` 常量、随机提供器、`add` | 展示区分声明形式；附魔签名仍折叠，提示不丢其他函数 |
| 子表函数 + 引用 entry 函数 + 父 pool/table 函数 | 观测顺序符合执行顺序；不要求标出唯一 JSON 位置 |
| `sequence`、`filtered` 命中/不命中、`reference` | 只报告实际进入的叶子，外壳和子调用不重复；缺失/循环引用安全降级 |
| `set_item` / 书转附魔书 / 熔炼后再修改组件 | 新对象继承正确追踪；最终产物能显示捕获片段，原版动态结果不标模组联动 |
| 数量达到或超过单栈上限 | 所有 splitter 副本继承链，同一轮概率只计一次 |
| 同一轮多个相同物品、不同函数链 | 兄弟物品不串链，不通过组件相同强行共用来源 |
| 容器设置/修改内容 | 容器显示内容函数摘要，内部物品函数不串到外层；内部物品不单独计外层掉落 |
| 两平台已知注入，自有追加/替换与同签名普通掉落 | 显示模组联动且保留普通来源；最终概率仍包含平台处理结果 |
| 无法解释的第三方函数/替换 | 可显示未解析/未完整捕获；基础模拟可继续，不猜 mod 或路径 |
| 首次计算、缓存恢复、切输入、LRU 淘汰 | 当前输入观测准确，淘汰后不借用其他输入；动态条目存在性不丢 |
| 改 modifier/tag/熔炼配方后重载 | 相关观测和概率按失效策略重算，旧代记录不混入新目录 |
| 无作用域的真实开箱/钓鱼/考古 | 无模拟记录泄漏；相同固定输入/种子下捕获开关不额外消耗随机数 |
| 异常、取消/换代、长链和大量分支 | 作用域清理；原执行异常如实失败；超限显式截断，不影响其他任务 |

性能核验使用同一套表、样本数、场景和参数，比较捕获开启/关闭的 tick 分片耗时、总耗时、唯一链数与截断数。允许存在开销，但须有可报告的数据，不能用减少样本数量来制造相同耗时。

## 八、待确认项
