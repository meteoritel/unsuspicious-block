# 文档撰写风格指南

本文档是 Unsuspicious Block 项目中所有文档（包括开发者文档、设计规格、API 契约、指南及 Agent 治理文档）的唯一撰写风格权威。无论是人类开发者还是 Agent 编写或维护文档，均必须遵循本文档约定的规范。

---

## 1. 上下文指针规范 (Context Pointers)

上下文指针（Context Pointer）是指常驻在上下文（如 `AGENTS.md`、`docs/README.md`、`docs/dev/README.md`）中，用于引导读者或 Agent 在特定条件下跳转至外置文档的引用。

### 1.1 指针编写三原则
1. **前置引导词 (Front-load leading words)**：将核心动作与触发领域置于行首，便于读者与模型第一眼完成模式匹配。
   - 推荐：`- 新增网络包：见[网络与同步](foundation/network.md)的「扩展点」`
   - 避免：`- 如果你想了解如何为模组添加新的网络数据同步包，可以参考...`
2. **一分支一指针 (One trigger per branch)**：严格合并同义触发条件，一个功能分支只分配一个明确触发入口，杜绝换马甲重复列举。
3. **剥离已知身份 (Cut identity the body already carries)**：指针仅负责说明“何时读、去哪读”，不在指针行内复述正文结论或枚举全部细节。

### 1.2 上下文负载与认知负载
- **上下文负载 (Context Load)**：指常驻于上下文的文字所消耗的 token 与注意力。`AGENTS.md` 中的每一行都会在每一轮对话中计费并分散注意力，必须极度精炼。
- **认知负载 (Cognitive Load)**：指读者索引和理解文档体系的脑力成本。非频繁查询的内容，应通过单层上下文指针外置到独立文档中。

## 2. 信息阶梯与渐进披露 (Information Hierarchy)

文档内容分为两类基本构件：**步骤 (Steps)**（按序执行的动作）与**参考 (Reference)**（按需查阅的规则、定义与事实）。两者在**信息阶梯**中自顶向下分层：

| 阶梯层级 | 内容形式 | 定位与读取时机 | 典型位置 |
|---|---|---|---|
| **Tier 1: 步骤序列** | In-file step | 任务的主干行动流程，按固定顺序执行 | `guides/` 中的工作流小节 |
| **Tier 2: 文件内参考** | In-file reference | 同一主题下的平铺规则、配置表或定义，就近聚合 | 各文档正文的表格与章节 |
| **Tier 3: 外置披露参考** | Disclosed reference | 跨分支特异细节、底层算法、历史背景，通过指针按需到达 | `dev/internals/`、`design/` |

### 2.1 渐进披露 (Progressive Disclosure)
- 当某一机制只有特定分支才会使用，或者细节极长会冲淡主干步骤时，必须将其推向下一级阶梯（下沉到 `internals/` 或独立文档），通过上下文指针按需唤起。
- 杜绝**认知膨胀 (Sprawl)**：单篇文档超过合理长度时，读者的注意力会被稀释，陈旧信息容易沉淀（Sediment）。应及时按职责或子序列拆篇。

### 2.2 就近聚合 (Co-location)
- 同一概念的定义、规则、限制与源码落点必须聚合在同一标题下，严禁碎片化散落在不同段落或多个文件中。
- 读完一个小节，读者即可获得该机制闭环的完整上下文。

## 3. 单一事实源与环境缓存原则 (Single Source of Truth)

1. **唯一权威出处**：
   - 领域术语以 [`GLOSSARY.md`](../../GLOSSARY.md) 为唯一事实源；
   - 文本格式与色表以 [`text-format.md`](../dev/foundation/text-format.md) 为唯一事实源；
   - 代码架构导航以 [`docs/dev/README.md`](../dev/README.md) 为唯一事实源。
2. **区别“环境真实”与“文档缓存”**：
   - 能从开发环境中瞬时查阅的单点信息（如 `gradle.properties` 中的版本号、CLI 的 `--help` 参数列表、类的公开方法签名），文档**不作冗余镜像缓存**。
   - 文档只记录“环境无法自我坦白的事实”：**架构意图、设计权衡、生命周期假设与避坑点 (Gotchas)**。

---

## 4. 正向引导与引导词 (Positive Prompting & Leading Words)

### 4.1 正向表述优先
- 避免大量使用“不要做 X”、“禁止 Y”的否定式表述。认知模型和人类阅读时，强烈的否定词会先激活被禁行为的注意焦点（"Don't think of an elephant" 效应）。
- 优先使用肯定句阐述标准做法：
  - 推荐：`颜色统一从 TooltipBuilder 语义常量取值`
  - 避免：`严禁使用 ChatFormatting，也不要手写十六进制颜色`
- 仅当作为不可妥协的硬性安全红线（如多平台模块隔离禁令）时才保留清晰的正向约束加红线警示。

### 4.2 项目核心引导词 (Leading Words)
使用在预训练与项目共识中具备强先验概念的词汇，以最小 token 锚定统一行为：
- `tight`：紧凑、低开销、确定性强的执行循环。
- `fail-fast`：遇到不合法状态立即报错中断，不隐蔽降级。
- `single-source`：单一事实源，一处修改处处生效。
- `progressive-disclosure`：渐进披露，主干干净，细节延迟到达。

## 5. 步骤与可检验完成条件 (Completion Criteria)

任何行动步骤或实施计划，必须以**客观可检验的完成条件**收尾，杜绝主观模糊标准：

| 模糊表述（禁止） | 可检验表述（推荐） |
|---|---|
| “确保文档编写规范且没有错误” | “运行 `python tools/checks/check-docs.py` 退出码为 0，无未达链接” |
| “更新各处相关引用” | “全仓库检索目标关键词，确认匹配结果为 0 处孤立旧路径” |
| “完成代码重组” | “执行 `./gradlew.bat build`，构建通过且各模块产物生成成功” |

## 6. 排版、图表与自动化门禁 (Formatting & Gate)

1. **标题层级**：正文使用 2 至 4 级标题（`##`、`###`、`####`），编号保持连续，避免深层嵌套。
2. **相对路径规范**：所有文件内相对链接必须严格基于当前文件的相对路径，且必须指向真实存在的文件：
   - 交叉引用使用相对路径：`[显示文本](../dev/foundation/architecture.md)`
   - 严禁包含空链接或指向未入库文件的占位链接。
3. **图表与代码围栏规范**：
   - 全部代码围栏必须显式标注语言（如 `java`、`json`、`mermaid`、`text`）。
   - **流程图、状态流转、调用链、时序交互、依赖与类关系图**统一使用 `mermaid`（`flowchart`、`sequenceDiagram`、`classDiagram`），不再新增纯文本 ASCII 框线流程图；节点文本含括号、冒号、斜杠或特殊符号时使用双引号包裹（如 `A["文本 (说明)"]`），避免在标签中嵌入 HTML 标签。
   - **目录树、命令行清单、存储键与路径模板**保留在 `text` 代码围栏中；纯字段列表优先使用 Markdown 表格。
4. **内容演进与换行**：
   - 修改已有机制时，将更新内容融入对应章节与表格中，不直接在文档或章节末尾堆叠零散“补丁段落”。
   - 所有 Markdown 文档统一使用 UTF-8（无 BOM）与 **LF** 换行符。
5. **自动化门禁**：
   - 提交任何文档修改前，必须运行：
     ```powershell
     python tools/checks/check-docs.py --include-local-rules
     ```
   - 工具将自动核验入口可达性、相对链接有效性与导航登记，必须返回退出码 0。
